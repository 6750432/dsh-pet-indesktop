## 0. 一句话结论

**改，没问题**——MIT 许可，本地自用与二次发布都允许喵。
但方案里有三件事必须先说清楚喵，否则这个"性能对比 md"会变成自欺欺人的东西喵：

1. **代码风格重构（拆 God 类、消循环依赖）不会让 CPU 降低哪怕 1%** —— 性能 md 里不能拿它当卖点喵；
2. **真正影响性能的是素材规格与渲染路径**（我们上一轮就是这么把 CPU 从 51.6% 打到 11.5% 的）喵；
3. **跑对比要真的把桌宠跑起来** —— 这是整个方案里唯一需要你点头的"重"动作喵，其余全是读代码喵。

## 1. 法律面：能不能改，改完要注意什么

| 项 | 结论 |
|---|---|
| 主仓库许可 | **MIT License**，`Copyright (c) 2026 Merzlin` |
| 能不能改 | ✅ 能。MIT 允许修改、使用、再发布（含闭源） |
| 唯一硬义务 | 保留 `LICENSE` 与版权声明；分发派生版时注明"已修改" |
| 本地自用 | 事实上无任何义务（因为不涉及分发） |
| ⚠️ 素材（`assets/`） | **是另一码事**：`THIRD_PARTY_NOTICES.md` 单独声明第三方资源授权。改代码没问题；**把改造版连素材一起对外分发前，要单独过一遍素材授权** |
| 你自己的规矩 | 你定过"这份东西不外发"——这条一执行，上面那条风险自动归零 |

**另有一条必须遵守的作者红线**（他写在 `requirements.txt` 里）喵：

> 「许可证是硬约束：**不要换成流传更广的 lunardate / zhdate**。那两个都是 GPL-3.0-or-later，而本项目是 MIT，**引入即造成 copyleft 传染**。」

⇒ 我们加任何新依赖（RAG 的向量库、嵌入模型等）都必须先过许可这道关喵，**别替他往 MIT 项目里灌 GPL**喵。
⇒ 好消息：`sqlite-vec`（Apache-2.0）、`bge-m3`（MIT）、`onnxruntime`（MIT）都不踩线喵；真要用 GPL 的，就只在我们本地跑、不进补丁喵。

## 2. 现状盘点：其实我们已经改了

`~/dsh-pet-opt` 就是一份本地改造版，只是还没规范化喵：

```
git status  →  118 个文件有改动
git diff    →  110 files changed, +206 insertions(−4)
                其中【代码只碰了 3 个文件】：pet/catalog.py、pet/app.py、pet/window.py
                （外加 1 个测试文件）；其余 104 个全是 webm 素材的重编码
                我们的 scripts/ 目录改动数 = 0
patches/    →  0001-本地扩展包与画布自适应.patch（9.8 KB）
                0002-无帧时不占输入区.patch（5.9 KB）
```

**判断**：代码改动只有 **+206 行、3 个文件**，素材改动才是大头喵。这说明一件事——**这个项目的性能提升空间几乎全在素材与帧策略上**，不在源码结构里喵。

## 3. 变更管理怎么定（比"改不改"更重要）

现在的做法是"在源码树里直接改"喵，能跑，但会有三个后果喵：① 上游一更新就冲突到怀疑人生喵；② 分不清哪个改动是关键喵；③ 素材改动混进 git 历史（二进制，diff 无意义）喵。

**建议改成这样**喵：

| 规则 | 做法 |
|---|---|
| 分支 | `upstream/main` 保持干净；我们的活全在 `local/dsh-opt` 分支 |
| 一事一补丁 | 每枚补丁只做一件事，提交信息写"为什么"（不是"改了什么"） |
| 补丁必带验收命令 | 例如"运行 X 后 CPU 应 ≤ Y%"或"该功能应表现为 Z" |
| **素材不进 git** | 只提交 `scripts/转320x180-72fps.sh` + 一份校验和清单；素材用脚本可复现地重建 |
| 上游跟进 | `git fetch upstream && git rebase`；**改动文件越少，越不痛** |
| 大文件敬而远之 | `window.py`(4648) / `app.py`(3411) / `agent_link.py`(5003) 不碰，除非功能必需 |

### P1 · 低风险高收益，建议这次做（≈半天）

| 4 | 素材转码脚本固化 + 校验和清单 | 脚本 | 可复现，不再依赖我的手艺 | 无 |

> **P1-3 的首选目标已经找到了（今天核实的）**：
> `pet/webm_clip.py:1853` 的帧长度校验失败时是**静默 `return None`**——没有日志、没有计数；
> 而**同一个文件** `webm_clip.py:2597` 的同类校验却是**有 warning 的**：

## 5. 性能对比设计（这就是那份"单独 md"的骨架）

### 5.1 先定口径：两类指标，绝不能混在一张表里

| 类别 | 指标 | 适合衡量的改动 |
|---|---|---|
| **性能类** | CPU%（空闲 / 播放中，均值+峰值）、RSS 内存、启动到首帧耗时、线程数、掉帧计数、温度 | 素材规格、解码路径、定时器密度、渲染合成 |
| **结构类** | 核心侧对 `pet.chat` 的引用数（现 42）、循环依赖组数（现 6）、最长函数行数（现 733）、God 类行数（现 4309） | 拆分、外挂化、解耦 |

**红线**：谁要是拿"拆了 God 类"去解释"CPU 降了 0.3%"，那就是在编数据喵。两类指标分两张表喵。

### 5.2 变量控制（上次踩过的坑）

| 变量 | 规定 |
|---|---|
| 机器 | 同一台，全程不重启、不切内核 |
| 配置目录 | **写死 `~/.config/dsh-pet-standalone`**（源码版用的那份）。两份配置（4.3M / 11M）不能混用 |
| 启动方式 | 一律 `.venv/bin/python -m pet`（cwd = 被测源码树），通过 `启动桌宠.sh` 拉起 |
| 背景负载 | **不关你的程序**（Cherry Studio 常占 ~125%，上次的教训）。改为：每个场景记录背景 CPU，报告里并列，桌宠的数字取**净增量** |
| 时长 | 每场景 **60 秒**，串行执行，场景之间留 30 秒冷却 |
| 重复 | 每场景 **≥3 次**，报中位数 + 区间（min~max） |
| 素材 | 固定同一套：`click/` 里同一个动作 + `idle` 同一个动作 |

### 5.3 用作者自己的 bench（这一条最关键）

上游自带两个基准脚本喵，**用他的口径跑，结论才不会被质疑**喵：

```
scripts/bench_idle_decode_throttle.py     ← 空闲解码节流
scripts/bench_music_lyric_align.py        ← 歌词对齐（本机 Linux 可能不适用）
```

我们额外加一个自写的轻量采样器（只读 `/proc/<pid>/stat`，不装任何东西）喵，每 200 ms 采一次，输出 CPU%/RSS/线程数喵。

### 5.4 基线取谁

建议**三段对照**，比"前后对比"信息量大得多喵：

| 段 | 内容 | 来源 |
|---|---|---|
| A · 上游原版 | v4.2.1 未打补丁 | `~/Desktop/桌宠审计-2026-09-26/原仓库-只读`（已就位，文件只读，跑它只读不写代码） |
| B · 上轮改造版 | 我们现在这份（素材已转 + 206 行补丁） | `~/dsh-pet-opt` |
| C · 本轮改造版 | 加上 P1 四项之后 | 新分支 |

产出表：`A vs B vs C`，每格"中位数（区间）"喵。

### 5.5 这份 md 的最终结构（预定）

```
1. 测试环境与变量控制（含背景负载记录）
2. 三段对照表：性能类指标
3. 三段对照表：结构类指标
4. 逐项结论：哪个改动值多少（不许含糊，要能归因到具体补丁）
5. 复现步骤（复制粘贴可跑）
6. 没测到 / 测不准的部分（诚实列表）
```
